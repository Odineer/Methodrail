# v0.10 knowledge-loop protocol

Status: frozen 2026-09-20. Qualitative dogfood, not an empirical comparison.

This protocol runs typed-note accumulation on real work for four calendar weeks, then answers the Stage 4 questions with snapshots and ledgers instead of taste.

## Duration

Four calendar weeks from the first confirmed `/methodrail-init` (preview → confirm) on the second repository. Methodrail's existing harness does not start that clock.

Work weekday for snapshots: Sunday. First Methodrail snapshot may be taken as a week-0 baseline after this freeze; weekly pairs are due each Sunday thereafter until week 4.

## Per-repository setup

1. Run `/methodrail-init` once. Preview, then confirm. Pick harness placement (in-repo `.methodrail/` or linked-external).
2. Record: date, harness placement, `PROJECT.md` line count after init.
3. Do not seed typed notes during init. Init reports candidates; `reflect` is the only writer of `.methodrail/knowledge/` typed notes.

## Daily work

Work normally with `/develop`, `/debug`, `/investigate`, `/refactor`. Do not invent sessions for the loop.

At the end of every non-trivial session, run `reflect`:

- Accept every proposal that is honestly earned from that session's evidence.
- Decline the rest.
- Write one line per declined proposal in that week's log (reason only).

One governance mutation per approval remains in force. If `reflect` produces ≥2 independently earned accepted candidates, persist at most one after approval and record the remainder as throttle hits.

## Weekly measurement (same weekday)

From the Methodrail checkout:

```bash
npm run knowledge-snapshot -- <repo> --out docs/internal/knowledge-loop/<repo_key>/<date>.json
npm run ledger -- summarize > docs/internal/knowledge-loop/ledger-<date>.md
```

Rules:

- Only Methodrail's own snapshots and the ledger summaries are committed.
- Other repos' snapshots are copied in sanitized form: omit absolute paths, workspace roots, and file contents; keep `repo_key`, `git_head`, `date`, and the numeric health fields.
- Do not relabel historical snapshots after seeing later weeks.
- `git_head` is null when the path is not a git toplevel (fixtures, nested dirs).

## Week-4 metrics

Answer all of the following in `docs/internal/v0.10-knowledge-loop-results.md`. That file is Task 3.4 and must not be written before four weeks of snapshots exist.

- Notes created / proposals declined
- `review-required` transitions and how many were reconciled
- Sessions where a `.methodrail/knowledge/*.md` read preceded the first edit (ledger `harness_reads`)
- Sessions where `reflect` produced ≥2 accepted candidates but only one could be persisted (the one-mutation-per-approval throttle)
- Sessions ending with edits and no verification command

Include the sentence: qualitative dogfood, not an empirical comparison.

## Throttle decision rule

If ≥3 sessions hit the one-mutation cap with independently earned candidates, open a follow-up to allow N approved mutations per `reflect` transaction with per-note validation.

Otherwise keep the current rule.

Write the decision into `references/knowledge/lifecycle.md` only after that follow-up ships with evals. Do not edit the lifecycle reference from snapshot counts alone.

## What this protocol does not do

- It does not add a second control plane or a consumer CLI.
- It does not auto-apply `reflect` proposals.
- It does not prune skills (Stage 4 waits on this data).
- It does not claim general improvement from note counts.
