## 2. Problem and success criteria

Methodrail already owns the major lifecycle capabilities. Its principal gaps are inconsistencies between parent workflows and leaf procedures:

- `develop` mentions `code-review` in its overview but has no explicit code-review checkpoint in its numbered procedure.
- Routine test seams and ticket breakdowns can require human approval even when they contain no unresolved product choice.
- `wayfinder` restricts non-research decisions to one per session and can default to grilling.
- `architect` and `code-review` can escalate because the host supports agents, without a separate cost or independence justification.
- `refactor` can reject quiet or unused targets even when the requested change has a demonstrated benefit.
- Debugging includes a fixed hypothesis quota and an ambiguous discussion requirement after failed attempts.
- Specs and tickets do not consistently preserve the connection from acceptance criteria to the existing verification procedure.
- Composed leaf gates and parent workflows can both request final completion reports.
- Eval records measure skill reads, references, agents, and latency, but not reported token usage.

These are instruction-level findings. Four recorded live runs tagged `develop` listed no `code-review`, but their operator summaries are not a representative triggering-rate measurement and do not prove that informal review never happened.

The release succeeds when a native agent can complete a well-defined feature autonomously, use the existing verification capability, perform a proportionate review, and ask one batch only when unresolved human choices materially determine the result. Mechanical work must retain its cheap path.

## 4. Human-decision policy

Canonical owner: `references/decision-frontier.md`.

### 4.1 Both conditions must hold

A clarification about what to build is justified only when:

1. Human judgment is necessary. The answer concerns user intent, preference, policy, or an intentional tradeoff and cannot be settled by the current request, prior answers, established project guidance, source, tests, documentation, configuration, runtime evidence, or a suitable experiment.
2. Different answers materially change the build. They change observable behavior, meaningful scope, permissions, data handling, public compatibility, or acceptance criteria.

The existence of multiple technical approaches does not establish either condition. Technical uncertainty normally calls for investigation. An established convention or supported low-impact reversible choice can be selected autonomously.

Prior authorization and answers remain resolved. Do not ask again simply because execution enters a different skill. A consequential unresolved choice must not be treated as approved after a timeout or absence of a reply.

### 4.2 Batch the qualified current frontier

Before asking, gather evidence and filter questions through both conditions. Ask the currently actionable, mutually independent qualifying questions in one round. Group related questions for readability. Questions whose prerequisites are unanswered remain for a later round.

Each question must include:

- The unresolved choice and relevant known facts.
- Meaningful alternatives.
- What would be built differently under those alternatives.
- A recommendation and its tradeoff.

Do not manufacture questions to fill a batch. If no question qualifies, continue autonomously. If one qualifies, ask that one.

Pause only implementation that depends on unanswered choices. Continue independent investigation or authorized work. Recompute the frontier after receiving answers.

Example: an export with unresolved field scope and output format may ask both together. The field scope changes data exposure; the format changes the interface. Helper naming, a documented date convention, and a repository-supported test seam do not enter that batch.

### 4.3 Clarification, permission, and access are different

This policy governs design clarification. It does not erase an existing explicit approval boundary for ADRs, typed notes, harness placement/writes, or consequential external operations. Reuse approval already present in the session.

When a necessary environment or redacted artifact is genuinely unavailable after reasonable attempts, report the concrete blocker and request only the missing input or access. Do not turn that blocker into a requirements interview. Never ask the user to paste secrets into the conversation.

### 4.4 Apply the policy consistently

- `develop`, `debug`, `refactor`, `investigate`, and authorized maintenance repairs link to the shared rule where relevant.
- `to-spec` chooses supported test seams autonomously unless a seam encodes a qualifying unresolved human decision.
- `to-tickets` chooses routine granularity and dependency edges autonomously. Replace its unconditional quiz/approval loop.
- `grill-with-docs` and its grilling reference retain frontier rounds, recommendations, and fact-finding, but filter ordinary workflow questions through the shared rule.
- When qualifying decisions are resolved, report the resulting understanding and follow the caller's existing authority. Do not add another ceremonial approval of the same decisions.
- A standalone interview still ends with its synthesis; it does not automatically authorize implementation.

## 5. Review selection and lifecycle checkpoint

Policy owner: `references/rigor.md`. Procedure owner: `skills/code-review/SKILL.md`. Separate review workflow: `skills/review/SKILL.md`.

### 5.1 Review is required for substantive implementation

`develop` must explicitly invoke the canonical `code-review` procedure before completing a substantive change. This includes behavior-changing production code, meaningful interface/contract changes, and configuration changes that materially affect behavior or safety.

Substantive structural repairs in `refactor` and nontrivial production-code bug fixes in `debug` use the same selection policy. A one-line change can be substantive; file or line counts are not sufficient classifiers.

Mechanical edits, copy changes, deterministic regeneration with an adequate canonical check, and other low-impact changes retain quick diff inspection and appropriate verification. They need no automatic review skill or reviewer agents. An explicit user request for review still invokes review.

### 5.2 Review depth

| Situation | Required approach |
|---|---|
| Mechanical task in a writing workflow | Quick task-delta inspection and the adequate existing check |
| Bounded substantive change | `code-review`, with distinct Standards and Spec passes in the current context |
| Sensitive or consequential cross-boundary change | Isolated independent review when the host supports it and independence meaningfully reduces risk |
| Host cannot provide isolation | Separate local passes; disclose the independence limit without pretending an independent review occurred |
| User explicitly requests a stronger review mechanism | Honor the request within its scope and existing invocation boundaries |

Security-sensitive authorization, sensitive-data handling, hard-to-reverse migrations, concurrency, shared public contracts, and consequential architecture are strong signals for independent review. A capability merely being available is not an escalation reason.

Keep Standards and Spec distinct in local and isolated modes. Scope security, performance, architecture, and test-effectiveness checks to relevant portions of the change; do not add five public review axes or a second review skill.

`interrogate` remains suggest-only. Required ordinary review does not silently invoke it.

### 5.3 Parent supplies the review target

For composed review, the parent supplies the original request, acceptance criteria, task-owned delta, base/state information, relevant standards, verification evidence, and known deviations using `references/protocols/review-packet.md`.

Capture enough initial worktree information to distinguish the agent's changes from pre-existing user work. Inspect necessary surrounding context without treating unrelated edits as permission to change them. Include applicable staged, unstaged, and untracked work within the requested review scope.

A composed reviewer must not ask the user to supply a base or spec already present in its packet. Standalone review should resolve its range and intent from the request and repository before seeking missing human input.

### 5.4 Review content and action

Review the actual implementation and relevant tests against:

1. Requested behavior, acceptance criteria, and scope.
2. Applicable repository standards and ownership/contract boundaries.
3. Relevant edge and failure paths, including security or performance consequences when applicable.
4. Whether the verification actually exercises the claim.
5. Whether assertions, tests, thresholds, suppressions, or check configuration were weakened to obtain a pass.

Changing a test is not inherently wrong. Assess whether the change follows an authorized requirement change or corrects a defective oracle. Reject unjustified weakening of still-valid expectations. Do not universally prohibit suppressions or test deletion when a legitimate, evidenced reason exists.

In writing workflows, repair material findings within the authorized task, then verify affected state. Optional suggestions do not automatically expand scope. A standalone `/review` remains read-only unless fixes were requested.

A review loop ends when material findings are resolved, a concrete blocker remains, or a genuine consequential human choice must be settled. New external scope is reported rather than absorbed into the task.

## 6. Existing verification remains the mechanism

Owners: `references/verification-lifecycle.md`, `skills/verify-change/SKILL.md`, and the project's established verification artifacts.

The implementing agent must first select the relevant existing verify skill, feature-map flow, control guidance, tests, scripts, runtime procedure, or other suitable evidence mechanism. Select according to the changed behavior and the claim being made.

Specs state required observable outcomes. Tickets identify the relevant existing verification procedure and the scenario/expected result. They do not copy launch, readiness, drive, reset, or cleanup instructions into each ticket.

Creation and maintenance retain their current triggers and ownership:

- Adequate existing verification is reused.
- A real missing reusable path can justify task-scoped creation within existing authority.
- A mapped behavior change or affected helper can justify task-scoped maintenance.
- Broad work does not automatically imply a full verification audit.
- Product defects return to the writing workflow; they do not cause the verification oracle to be rewritten to match a bug.

### 6.1 Execution sequence

For a normal feature, the conceptual sequence is:

    understand and resolve qualifying decisions
    -> establish acceptance criteria and select existing proof
    -> implement in meaningful slices with appropriate evidence
    -> review the substantive task delta
    -> fix material findings
    -> rerun verification invalidated by later edits
    -> apply verify-change to the final claims
    -> report once from the owning workflow

This is not a mandatory chain of full skill loads. A shared check can prove several outcomes. Existing TDD loops and project verification run at the appropriate boundaries.

### 6.2 Evidence freshness and reuse

Keep the rule that completion evidence must be produced in the current turn against unchanged relevant state. Reviewing old author evidence may inform a review, but does not become a claim that the current agent ran it.

Within a turn, reuse a complete successful result when it still proves the claim and no relevant state changed. Do not rerun a check merely because another leaf skill was entered. If review fixes, cleanup, harness maintenance, or a later repair invalidate the evidence, rerun the affected checks. Do not weaken the fresh-evidence rule to reduce tokens.

Clarify the gate procedure accordingly: identify the needed evidence; reuse qualifying current-turn evidence or run the complete relevant procedure; inspect the full result; judge the claim; report it accurately.

Methodrail itself has no user-facing runtime requiring a new `verify-project` skill. Its established maintainer checks are sufficient for this implementation.

## 7. Specs and tickets

Owners: `skills/to-spec/SKILL.md`, `skills/to-tickets/SKILL.md`, existing task/review packets, and project-native artifact locations.

### 7.1 Specification readiness

Extend the current spec structure with observable acceptance criteria and explicit material boundaries. Preserve problem, solution, user stories where useful, implementation/testing decisions, and out-of-scope content.

Before describing a spec as ready for dependent implementation, verify that its current acceptance criteria are testable and qualifying human decisions are resolved. Return unresolved qualifying decisions to the parent; do not silently choose the most convenient behavior or start an unconditional interview from `to-spec`.

Do not manufacture numerical performance or coverage thresholds. Reuse existing project standards and user decisions. Existing docs, constraints, tooling, and commands remain canonical pointers.

Durable specs are created when requested or when substantial work justifies a reusable artifact. A tiny edit does not acquire a spec document merely to satisfy the lifecycle.

### 7.2 Ticket requirements

Every implementation ticket records:

- The bounded observable outcome.
- Acceptance criteria it satisfies, by concise reference when a spec exists.
- Blocking dependencies.
- The relevant existing verification pointer, scenario, and expected result.
- Any real prerequisite or coverage gap that prevents execution.

Use the existing project format or tracker conventions. A compact local example is:

~~~markdown
# Ticket: Export approved customer fields

Outcome: customer export includes only the approved profile fields.
Acceptance: spec's export-scope and CSV-output criteria.
Blocked by: export scope and format decisions resolved in the spec.
Verification: existing verify-project / customer-export flow;
exercise a customer with invoices and payment methods;
confirm those fields are absent and the CSV header matches the approved schema.
~~~

Do not duplicate the verification skill's driving instructions. Do not invent a new criterion-ID scheme or task database. Readiness and blockers should be explicit in the project's existing notation.

Check that the ticket set covers the spec's required outcomes and has no invented scope. Prefer complete verifiable slices; use contract-first or risk-first ordering when justified by the real dependency structure. Keep the existing expand/contract exception for wide refactors.

Protect existing incomplete plans and other agents' tickets. Prefer an existing feature-specific location or an unoccupied scoped path. If replacement genuinely requires a human scope/ownership choice, explain that conflict; do not overwrite another effort to avoid asking.

Maintain the active spec/tickets when implementation evidence changes their relevant decisions or verification expectations. A technical plan adjustment that preserves intended behavior can be made autonomously. A qualifying product change requires the human decision before dependent work.

## 8. Changes by main workflow

### 8.1 `develop`

Update `skills/develop/SKILL.md` so its numbered procedure and examples agree:

1. Use the shared human-decision rule and batched frontier.
2. Preserve proportional acceptance criteria and existing verification selection.
3. Keep TDD or another honest strategy at the relevant seam.
4. Insert explicit `code-review` selection/execution after the substantive implementation and before final completion.
5. Address material findings without restarting a separate lifecycle.
6. Perform task-scoped verification maintenance only under its current trigger.
7. Verify the final relevant state after later edits and produce the owning completion report.

The normal-feature and large-redesign examples must follow the same conceptual order. The mechanical path stays inspect, edit, adequate check. Separate `/review` is still useful when the user requests a standalone review; routine delivery uses the leaf `code-review`.

### 8.2 `debug` and `diagnosing-bugs`

Preserve the agent-runnable red-capable loop, reproduction/minimization, causal probes, fix at the contract owner, regression evidence, cleanup, and final original-scenario verification.

Replace the fixed three-to-five hypothesis requirement with one or more ranked falsifiable hypotheses proportional to uncertainty. One strongly supported hypothesis is acceptable for a sharply reproduced failure. Competing plausible mechanisms warrant alternatives. Do not generate filler theories.

After three unsuccessful fixes for the same symptom, stop speculative patching and reassess the reproduction, oracle, assumptions, contract owner, and architecture. Another fix requires a revised causal claim and new supporting evidence. This is not permission for a fourth guess, nor an automatic requirement for a human meeting.

Ask the user only if the reassessment reveals a qualifying human decision, missing actual authority, or concrete unavailable access. Preserve autonomous investigation otherwise.

Choose review depth from the shared policy for the resulting code change. Avoid duplicating the diagnosis procedure in `debug`.

### 8.3 `refactor`

Replace the unconditional quiet/unused-target stop with a relevance and benefit test. A named target may be quiet or unused and still have evidenced maintenance, packaging, contract, or tooling cost.

Keep unsupported speculative cleanup outside scope. Prove relevant behavior preservation using existing baseline checks. Before removing unused code, consider exports, dynamic loading, side effects, generated registration, and external compatibility; absence of local callers is not proof of dispensability.

Preserve the architecture-survey/selected-execution split. Intentional behavior changes explicitly requested alongside restructuring receive a bounded feature owner/phase rather than being silently called behavior-preserving.

Apply the shared review policy. Maintain affected verification helpers when structural moves invalidate their instructions, while retaining the intended behavior.

### 8.4 `review`

Keep the standalone workflow read-only. Consume its supplied packet, existing evidence, full requested diff, and appropriate blast-radius information. Fixes require the existing task authority; a finding alone does not authorize product edits.

Resolve duplicated formatting requirements between parent and leaf: `code-review` returns separate Standards and Spec findings with severity and evidence; `/review` presents a concise prioritized result while retaining each finding's dimension. Do not force two separate final user-facing reports and another duplicated summary.

Use the shared selection policy for local versus isolated reviewers. Validate verification effectiveness where the diff makes that relevant. Keep fresh evidence and supplied historical evidence honestly distinguished.

### 8.5 `investigate`

Keep cheap evidence routing, relevant knowledge reuse, confidence labels, direct answers, and read-only scope. Do not add a repository survey, spec, review, or verification-generation phase.

An unknown technical fact should lead to the next suitable evidence source or an explicit limit. Ask for genuinely necessary missing user intent or unavailable inputs; do not ask the user to answer discoverable facts. Discovery of a potential implementation does not authorize implementing it.

### 8.6 `methodrail-init` and `refresh-model-routing`

Keep artifact adoption by pointer, existing instruction preservation, validated harness placement, preview/apply distinction, one thin integration, and no-op refresh behavior.

During refresh, inspect only relevant affected roles and dependencies. Once an adequate verification path is established, reuse it rather than repeating full launch/drive discovery. Keep creation discovery available when a real new surface or missing path warrants it.

Keep initial model-policy discovery under existing initial-harness policy. For an unchanged valid existing policy, ordinary or control-only refresh must not automatically research the model catalog or launch live probes. Model-policy discovery is justified by explicit model work, a missing policy when creating a harness, a relevant conflict, or demonstrated binding drift. Skipping catalog research does not prove current availability; retain its existing evidence labels.

Placement and non-empty harness-write approvals remain intact. Honor placement/preferences already supplied. Required remaining choices belong in a single relevant preview round where practical.

### 8.7 `maintain-project`

Preserve its audit/repair separation, evidence-backed relevance, bounded selected batch, revalidation, sequential shared-file repairs, and partial coverage reporting. Do not add operational lanes, a debt database, issue filing, or a second discovery sweep.

Align authorized repairs with the shared human-decision/review rules. Reuse existing task packets and acceptance criteria through specialist handoffs. Recheck earlier selected outcomes when a later edit invalidates shared evidence. This existing maintenance rule should be the model for other composed writing workflows.

Reuse supplied grounding rather than restarting `how` when the packet already establishes the relevant state. Investigate missing facts or changed state selectively. Keep native model-role selection and graceful host degradation.

## 11. Optional native usage measurements

This is maintainer eval instrumentation, not a consumer runtime or new hook permission mechanism.

Extend the existing `EvalRun` shape with an optional native usage record. A suitable concrete interface is:

~~~typescript
interface NativeUsage {
  source: "native-report";
  scope: "complete-run" | "parent-only" | "partial";
  input_tokens: number | null;
  output_tokens: number | null;
  cached_input_tokens: number | null;
  total_tokens: number | null;
  artifact?: string;
}

// Added to EvalRun:
// usage?: NativeUsage;
~~~

Requirements:

1. Populate counts only from an actual native report or export. Preserve an evidence artifact when available. Do not add an SDK, make model calls for measurement, scrape unrelated account/session state, or put usage collection into permanent context.
2. Counts are nonnegative finite safe integers or null. Missing usage remains absent/null, not zero. Reject malformed supplied records; accept all historical records without usage.
3. Define `input_tokens` as inclusive of cached input. Normalize split host counters only when their semantics are documented; otherwise keep the uncertain normalized field null and preserve the report. Cached input is a subset and must not be added again to a total.
4. Keep `total_tokens` null unless the report provides a trustworthy compatible total. Do not infer actual prompt usage from file characters, skill counts, or metadata estimates.
5. `complete-run` includes all known child/reviewer usage without double counting. Parent-only and partial measurements must remain labeled and must not be presented as full task cost.
6. Compare token deltas only for compatible measurements with the same host/model, task scope, and coverage semantics. Report incompatibility or absence plainly. Token counts are not dollar cost or reasoning-quality measurements.
7. Preserve the existing skill, reference, agent, verification, and latency metrics as useful separate measures.
8. Carry usage through parsing, scoring, and comparison reporting. If both sides lack usage, existing comparisons remain compatible without fabricated zero-cost claims.

Expected implementation surfaces: `src/eval/types.ts`, `src/eval/load.ts`, `src/eval/score.ts`, `src/eval/compare.ts`, and focused tests. Only extend ledger conversion if an existing captured native payload actually contains suitable usage; keep the hook observational and fail-open.
